## 二、先复现真实故障，不预设根因

用户目前反馈：本地连接 DeepSeek 经常报错，修改后仍不能稳定完成任务，生成的问题也不够准确。历史记录仅作为线索：

- 曾出现 `fetch failed`、TLS/代理连接失败，系统代理曾指向 `127.0.0.1:7890`。其他扩展的同期错误不能直接证明 Code2Offer 使用了同一路径。
- 曾发现已安装同版本扩展与工作区 bundle 哈希不同，但这本身只能证明构建不一致，不能直接断言 VS Code 的同版本安装机制是根因。
- 曾在单文件阶段 1 测试中出现多次截断、推理预算耗尽及降级摘要。此前切换模型的单次 A/B 有改善，不能外推为所有模型、所有仓库、所有阶段已经稳定。

执行以下工作：

1. 建立从用户点击生成到输出失败的最短复现路径，明确运行版本、模型、端点、配置来源、实际网络路径、并发数和失败阶段。
2. 分别复现：普通 Node 进程、真实 VS Code Extension Host、通过安装 VSIX 使用插件。三者结果分别记录，不能互相替代。
3. 对照直连与显式代理；采集 DNS、TCP、TLS、HTTP、响应读取和业务解析各层证据。只能得出证据支持的结论：443 可连接不代表 API 可用；健康检查成功不代表大请求、流式读取及并发也正常。
4. 输出根因清单，每项包括症状、触发条件、证据位置、最小复现、影响、修复和回归验证。未证实的原因标记为假设。
5. 先修阻断生成的可靠性问题，再逐步接入搜索和图编排，避免同时引入大量变量使问题无法定位。

## 三、网络连接与 DeepSeek 客户端专项整改

### 3.1 统一网络层与配置

- 建立清晰的传输层接口，使 DeepSeek、Tavily 与 LangChain 适配器共享经过验证的超时、取消、代理、脱敏和诊断机制，避免每个库各自使用不同的网络路径。
- 明确支持直连、显式 HTTP/HTTPS 代理，以及所选运行时真正支持的系统代理/环境变量策略。检查 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`、VS Code 设置、Windows 系统代理/PAC 的适用范围和优先级。无法支持的模式给出明确提示，不假装已继承。
- 配置代理端口可连只是一项检查，还应验证代理能否连接目标主机。区分代理认证、CONNECT 隧道、TLS、远端拒绝和 DNS 错误。用户选择代理时不得未经说明偷偷改成直连。
- 端点必须通过 URL 解析验证，限制协议、用户名密码、查询参数、重定向和跨源凭据传递。统一处理尾斜杠、`/v1` 与完整路径误填，禁止重复拼接 `/chat/completions`。
- API Key、endpoint 和 provider 的来源须明确绑定，不能从不同工作区拼出错误凭据组合。不能仅因为被分析仓库自带 key，就信任它指定的未知接收端点。
- VS Code 凭据优先使用 SecretStorage；兼容现有环境变量与 `.env`。配置页面显示来源与生效范围，不显示完整秘密。
- 不通过 `rejectUnauthorized=false`、关闭 TLS 校验或修改系统证书安全策略掩盖证书问题。

### 3.2 超时、取消与完整响应生命周期

- 特别检查 `src/core/deepseek.ts`：当前实现中 `fetch()` 返回后 `finally` 会执行 `cleanup()`，但 `res.text()` 位于其后。必须复现并修复“响应头已经到达、正文卡住时超时与取消保护失效”的问题。
- 超时和取消必须覆盖连接、响应头、完整 body/SSE 读取、退避等待、后续解析及图节点调度；失败和取消后释放连接、reader、定时器与事件监听器。
- 区分连接超时、首字节/响应头超时、正文空闲超时和请求总时限。增加最大响应体大小；不能无限积累正文或等待无意义心跳。
- 如使用流式响应，正确处理分段 UTF-8、SSE 跨块、心跳、空增量、终止标记、usage、半截 JSON、断流和重连。不得把部分输出缓存为完整结果。
- 响应已提交但结果未知的故障可能产生重复计费，应在统计中保留这一事实，不声称重试具备供应商未提供的 exactly-once 保证。

### 3.3 错误分类、重试和并发控制

- 保留安全的错误链、底层原因码、HTTP 状态和请求 ID，分别识别 DNS、代理、TLS、超时、重置、鉴权、余额、限流、模型不存在、参数错误、服务端错误、无效 JSON、空回答和截断。
- 按协议和真实返回区分处理 400、401、402、403、404、408、413、422、429、5xx。永久配置/鉴权错误停止当前生成并给出可操作诊断；瞬态错误有限重试。413 可通过缩小请求处理，不能原样无限重试。
- 使用带随机抖动的退避并遵守合理上限的 Retry-After。统一请求级、阶段级、LangChain、LangGraph 的重试总预算，避免多层重试相乘。
- 对持续网络故障建立熔断与恢复探测，停止排队请求，避免每个模块继续失败数次。429/拥塞时可降低并发，恢复时逐步放开。
- 并发任务不共享可变请求状态；一个任务取消不影响另一个任务。连接池、代理 dispatcher 和并发限制在目标运行时经过真实测试。
- 为取消设置可测指标：受控测试中 2 秒内停止新请求和活动读取；已抵达服务端的费用不承诺撤回。

### 3.4 模型能力与结构化输出

- 查阅当日 DeepSeek 官方文档和当前账户可用模型，不按记忆硬编码模型列表，也不把模型名含有 `flash/reasoner` 当作完整能力判断。
- 建立 endpoint/provider/model 维度的能力配置：thinking、JSON、工具调用、流式、上下文、输出限制、温度等。诊断时可做低成本能力验证并记录时间与来源。
- 检查 `reasoningPolicy` 是否真正落实到 API body。当前官方文档提供 `thinking` 控制；应优先验证同一模型显式关闭或调整 thinking 的效果，再与切换模型比较。
- 复核此前自动路由到 `deepseek-chat` 的策略，不假设别名长期存在，也不假设其底层模型固定。回退模型必须在当前端点可用、能力兼容且可配置；记录实际使用模型，而不只记录用户填写的模型。
- 严格 JSON 请求必须满足供应商的提示与格式要求，并通过运行时 schema 校验。将 JSON 语法完整性、业务字段正确性和代码事实正确性分开验证。
- `reasoning_content` 不能直接充当最终答案、JSON 结果或可背诵材料。不得把任意截断片段机械补括号后判为可靠完成。
- 截断恢复优先考虑限制输出结构、缩小批次、缩小证据范围、调整 thinking 或兼容模型；总预算有界，不能只靠不断增大 max_tokens。

### 3.5 用户可运行的诊断入口

新增“测试 DeepSeek 连接”和“导出脱敏诊断”命令，并提供 CLI 等价入口：

- 配置来源与 URL 校验 → 网络路径 → TLS/HTTP → 鉴权 → 最小 JSON 请求 → 可选的小规模并发验证。
- 每步展示耗时、成功/失败/未测、原因和下一步建议；不扫描无关地址或端口。
- 诊断与生产必须经过同一传输层和配置解析。不要出现诊断走直连而生成走代理的误导。
- 诊断默认不发送仓库源码。导出文件排除 key、代理口令、原始 prompts、私有代码及敏感请求参数。

## 四、把“代码到面试”准确性作为核心产品能力

### 4.1 证据优先的代码理解

- 对主要语言建立明确的支持层级：文件识别、语法/符号分析、框架理解、语义验证。新增扩展名不等于已完成某语言的深度支持。
- 按语言使用适合的解析器/编译器接口或 Tree-sitter 等工具，提取符号、签名、入口、调用关系、依赖、配置、路由、模型、异常分支和测试证据。动态调用无法确定时明确标注不确定性。
- 保留可靠的文本回退，记录回退原因。不能为方便要求所有用户额外安装 Python、Docker、数据库或多套运行环境。
- 排除生成代码、压缩 bundle、供应商代码、浏览器 profile、缓存和密钥。核心业务、依赖边界、关键错误路径、配置及测试要有覆盖；不能只选最大文件或出现最多关键词的工具脚本。
- 文档用于理解意图，代码和测试用于验证实现。注释不能当成已经实现的证明；发现测试文件不等于测试通过。
- 建立统一证据对象：文件、符号、真实行范围、内容哈希、仓库快照、证据类型和关联主张。全流程使用同一坐标系与证据 ID。
- 区分项目明确实现的事实、外部知识、推断和改进建议。不得虚构个人贡献、线上规模、性能提升、用户数或商业收入。

### 4.2 问题与答案规范

设计带 schema 的题目模型，至少包含：题号、面试方向、岗位级别、难度、目标模块/符号、问题、考察目的、答案要点、代码证据、关联 claim、追问、错误回答、评分标准、证据状态及必要的外部来源。

题目按实际项目覆盖：

- 业务与项目总览、架构与数据流、模块职责、关键实现；
- API、数据建模、状态管理、事务与一致性；
- 并发与取消、缓存、性能瓶颈、边界条件；
- 异常处理、重试、幂等、降级、可观测性；
- 安全、权限、秘密管理、输入输出边界；
- 测试、部署、依赖、版本兼容、运维；
- 技术选型横向对比、缺点与改进、系统演进；
- 仅当代码确有相关能力时生成 LLM/RAG、检索质量、评测、成本与工具调用问题。

要求：

1. 每道项目事实题可指出具体代码行为。对“没有实现某能力”的问题说明检查范围，不能从局部未发现直接推断全仓库不存在。
2. 答案先回答，再解释实现、依据、权衡和适用边界；提供可背诵短答及进阶展开。避免整段堆砌文件路径和通用定义。
3. 追问至少形成“实现 → 原因 → 故障或规模变化”的递进。评分锚点具体到答对什么、哪些结论不受证据支持。
4. 横向对比必须结合项目约束，既讨论所选方案的收益，也讨论其代价；外部知识与项目事实分别引用。
5. 根据 JD 和技术栈定制，但不得把 JD 中需要的技术写成项目已使用。与代码无关的八股内容单独归为拓展学习。
6. 综合字符去重、主题/符号去重及必要的语义去重；换一种问法不能当成覆盖更多能力。
7. 容量足够的基准仓库提供 100 道高质量题；小仓库允许减少题量并解释证据边界，不能为凑数反复出题或捏造功能。
8. 问题、答案与引用一起接受验证；行号存在不代表引用支持答案。任何未验证或有争议的结论都不得伪装为 pass。

### 4.3 校验与修复闭环

- 确定性校验检查 schema、路径、行号、内容哈希、符号、重复度、覆盖和输出一致性。
- 语义校验逐条核对 claim 与代码片段，包括否定陈述、错误处理、参数默认值、并发行为和版本条件。
- 校验器收到足够上下文并允许“无法判断”；模型一致意见不能代替证据。关键问题设置独立审阅或人工标注基准。
- 修复只针对失败题或失败 claim，设定修复次数上限；重新校验改动题与受影响内容，防止缓存旧裁决。
- 质量不足时输出部分完成及缺口说明，不以占位模块卡、合成摘要或自我评价充当完整成功。

## 五、真正集成 LangChain、LangGraph 与 Tavily

在现有 TypeScript 工程内优先采用适配当前 VS Code Node/Electron 的 JS/TS 版本。先核实包名、API、最低运行时、许可证和打包方式；不要直接安装 latest 后假设与所有声明支持的版本兼容。

职责明确：

- LangChain：模型适配、工具封装、检索接口、提示模板和结构化输出。
- LangGraph：状态、节点依赖、条件分支、有界并发、持久化 checkpoint、失败恢复、取消及事件。
- Tavily：在用户启用联网增强后补充公开的版本事实、官方技术资料和客观选型依据。
- 现有代码事实提取、质量门禁和渲染保留为可测试的确定性模块。

建议图节点：

配置与预算检查 → 仓库扫描 → 证据索引 → 模块分析 → 问题规划 → 本地证据检索 → 按需 Web 搜索 → 候选生成 → 事实校验 → 有界修复/去重 → JD 重排 → 材料渲染 → 质量门禁。

### 5.1 图与持久化要求

- 实际通过图执行主流程，而不是只安装依赖或画一张架构图。分阶段迁移现有代码，每一步有回归验证。
- Graph state 保存 runId、仓库快照、配置/模型/提示词/schema 版本、证据索引引用、题目、裁决、搜索来源、预算、错误和事件。
- 正式环境使用落盘的 checkpoint；进程重启和 VS Code 重载后能够恢复。内存 saver 只能用于明确标注的临时测试。
- SDK 适配层与自定义网络层不能各自叠加重试；所有调用共享总预算和取消语义。
- 节点重放必须考虑付费调用和文件写入的副作用，保存已完成结果，使用内容指纹与原子提交降低重复执行；不作无法保证的精确一次承诺。
- 基于文件内容、证据依赖、提示词、模型能力及搜索版本判断失效范围。禁止直接复用失败结果或不匹配的旧题库裁决。
- 设置图最大步数、递归/修复次数、并发、token 和搜索预算；持久化兼容迁移要有版本与回退策略。

### 5.2 Tavily 使用规范

- 增加独立的 Tavily 凭据配置、健康检查、开关、调用上限和缓存状态。缺少凭据或搜索故障时能完成仅依据代码的基础流程；不得假装已经完成联网增强验收。
- 用经脱敏的技术名称、库版本、公开概念和待核实问题生成查询。默认不向 Tavily 发送私有代码、仓库路径、内部名称、JD 原文或秘密。
- 先本地取证，再按需搜索；对相同问题去重和缓存。禁止每道题机械搜索一次，更不能无限搜索直到评分达标。
- 官方文档、标准和项目维护者资料优先，记录技术版本、发布时间（可得时）、访问时间、URL、相关内容摘要和 claim 关系。
- 查询和结果缓存有 TTL；历史结果标记访问时间。搜索摘要或 Tavily 自动答案不是无需复核的事实。
- Web 资料只能支持外部技术事实，不能证明本地项目采用了某架构、取得某性能或实现某功能。
- 搜索结果与网页正文视为不可信输入；防 prompt injection、恶意链接、SSRF、重定向绕过、HTML 注入和超大正文。内网模型端点的显式配置不能变成任意网页访问内网的通行证。
- 在报告里展示“源码证据”和“外部参考”两个来源，支持点击核对和关闭外部增强。
- 有工具调用时按供应商当前协议维护 assistant/tool 消息及必要字段，限制工具清单和参数，避免模型自行操作文件或执行命令。
- 用基准比较“无搜索”和“有 Tavily”的正确率、题目针对性、耗时与成本。增加工具只有产生可测收益才保留为默认路径。

## 六、独立输出、增量与任务生命周期

1. 每次生成创建唯一 runId 和独立输出通道，自动显示当前任务；命名至少包含项目、时间和不冲突的标识。同秒触发、多仓库并发也不串日志。
2. 保留旧任务日志供回看；可有可选总览，但当前任务界面默认呈现本次输出。任务卡可直接打开自己的日志、报告和目录。
3. 每次产物隔离；新建运行与恢复同一次运行语义明确。自定义 `--out` 的旧行为须说明并验证，不能未经说明覆盖已有报告。
4. 审计 `allocateRunDir` 的跨进程竞争、`carryForwardIncrement` 是否复制正在写入的状态、运行锁过期、历史任务选择和 latest 指针。
5. 只共享可验证的内容缓存和必要 checkpoint，避免每次复制整个缓存造成磁盘按运行次数增长。不得把上次最终报告当作本次已完成。
6. 缓存关联完整身份：仓库、内容、请求策略、实际模型、提示词、schema 和必要的外部资料版本。增量失效可解释。
7. 自定义输出目录必须从仓库扫描排除，防止报告被重新当源码分析。诊断、缓存、历史 runs 同样不得污染画像。
8. 取消、重载、崩溃、代理失联之后可恢复；日志通道、listener、定时器和任务数据按生命周期释放，历史清理必须可控。

## 七、商业化产品体验与内容呈现

以“配置容易、过程透明、结果可信、复习高效”为目标，而不是仅换配色。

- 首次使用向导：选择仓库、DeepSeek 配置与测试、可选 Tavily、运行模式、范围/JD、预算和输出位置。
- 明确区分未配置、连接失败、等待重试、正在生成、可恢复、部分完成、成功和取消，不让用户对着无限转圈猜测。
- 进度展示当前节点、已完成模块/题目/验证数量、耗时、重试、预算消耗与预估区间；预估必须随仓库规模更新。
- 报告具备项目讲解、架构/数据流、核心模块、技术决策、问答、追问、亮点防守、缺点改进、JD 定制、模拟面试、错题和复习计划。
- 文件引用可在 VS Code 中打开正确版本及行位置；源码变化导致引用过期时提示。外部引用可核查，状态与置信程度有解释。
- 搜索、难度/模块/岗位/证据状态过滤、隐藏答案、学习进度、键盘导航、打印/导出和深浅主题可靠可用。
- 图表基于证据生成；无法确定的依赖或数据流明确标注。禁止为视觉效果编造组件或业务收益。
- 学习进度按仓库和题库身份隔离，题库变化采用明确迁移策略。新版本不能让旧进度错误附着到不同问题。
- UI 兼容高对比度、中文路径、多根工作区、缩放和大报告。Webview 使用严格 CSP、文本转义和受限消息协议。
- 大仓库扫描、解析、索引与报告生成不得长时间阻塞 Extension Host；必要时分批、异步或工作线程处理。

## 八、测试与真实验收矩阵

### 8.1 网络与协议故障注入

覆盖：正常响应、DNS 失败、拒绝连接、代理离线/需认证、TLS 失败、CONNECT 失败、IPv4/IPv6 差异、429/Retry-After、余额不足、5xx、慢响应头、正文永久挂起、正文中断、超大正文、重定向、非法 JSON、空 content、只有 reasoning、length 截断、SSE 跨块和取消。

每项断言不只看是否抛错，还要验证请求次数有界、资源释放、取消传播、错误可读、无秘密泄露、失败结果不入成功缓存。

### 8.2 图执行与文件一致性

覆盖节点失败、重启恢复、进程中断、并发写 checkpoint、缓存损坏、配置变更、提示词变更、文件新增/删除/重命名/等长修改、两仓库并发、同仓库重复触发、新运行分配、用户取消和恢复。

### 8.3 内容质量基准

至少准备 8 个可重复基准：TS/Node、Python、Java/Kotlin、Go、Rust、C#/.NET、前端/跨端、混合语言或大型单体仓库；小项目与复杂项目都应覆盖。无法实测的语言或平台明确标记，不宣传为已全面验证。

为每个基准记录预期业务、关键模块、可验证事实、允许/禁止生成的结论及代表题。构建可复查的人工标注集合，至少审查 100 道题，分布在多个仓库、难度和类别；标注来源与评审者类型必须真实，代理审查不能伪装为人工审查。

比较现版与候选版，以及 Web 关闭/开启两种模式：引用有效性、claim 支持率、项目相关性、重复率、模块覆盖、回答可用性、耗时和 token/搜索成本。

### 8.4 真正的产品验收

- 从最终打包 VSIX 安装，在真实 Extension Host 内触发生产配置与网络路径，完成仓库读取、生成、验证、渲染和报告使用。
- 至少选 3 个代表性仓库，每个执行 3 次端到端真实运行；包含冷启动、增量、取消恢复。费用受预算控制，未跑的项不能写成通过。
- 至少对一个故障复现仓库执行修复前后对照。代理相关问题必须在实际宿主中验证修复，不能只用普通 Node 请求替代。
- 有 Tavily 凭据时完成一次真实联网增强端到端；无凭据时完成 mock/契约和无搜索路径，并把真实 Tavily 验收列为发布缺口。
- 验证新用户安装、旧版本升级、实际版本/哈希、设置与密钥保留、中文路径、多根工作区、独立日志/报告、断网、取消、恢复和导出。
- 验证声明支持的最低 VS Code 版本与当前稳定版。Windows 为必测；macOS/Linux 通过 CI 或实际环境记录覆盖，不以推测替代测试。
- UI 捕捉可用时完成实际操作和截图；不可用时使用其他可证明的交互测试，并逐项注明无法覆盖的视觉与交互检查。

## 九、定义可核验的 S 级门槛

S 是本项目的验收等级，不是行业认证，也不能由模型给自己打分得出。预先定义计算公式、分母、样本、环境与失败处理方式，禁止看到结果后降低标准。

建议采用 100 分量表：可靠性 30、代码与问答准确性 35、使用体验 15、性能与成本 10、安全与可维护性 10。各项细分及得分必须关联验证证据；总分至少 95 且以下硬门槛全部通过，才可记 S：

- 无未解决的阻断项、P0/P1 稳定性和安全问题。
- 网络故障注入必测矩阵通过，正文挂起可中止，取消后不持续创建请求，重试/图循环均有硬上限。
- 指定真实端到端矩阵全部完成；输出统计为“9/9 等有限样本结果”，不得据此宣称公网成功率为 100%。
- 发布题库中引用路径与行范围合法率为 100%；该项仅代表定位正确，不代表语义支持。
- 标注样本中项目事实 claim 支持率至少 98%、问题项目相关率至少 95%、语义重复率不高于 3%；关键项目身份、架构和安全事实不得有捏造。
- 发布题库不得把未验证结论标成已验证；失败/降级不会显示为完整成功。
- 受控测试中取消响应不超过 2 秒；并发任务日志、凭据、缓存、结果不串线。
- 真实测量大仓库事件循环延迟、内存、首个可用结果、完整耗时及成本；提供基于固定机器和 fixture 的可执行阈值，新增框架不能造成未经说明的显著回退。
- 内容质量不达标时优先减少题量或标注缺口，禁止通过降低标准或重复题凑满 100。
- 无密钥泄露、源码意外发送到 Tavily、未授权端点重定向、Webview 注入或可利用的路径逃逸。
- 1.0.0 安装包可安装、激活、升级和实际完成任务；历史产物可回看，版本与 bundle 可追溯。

未满足硬门槛则保持候选版本，提供已完成项、缺口与证据，不编造 S 评级或正式可用结论。商业可用意味着清晰的支持范围和受控故障恢复，不意味着第三方服务永不故障。

## 十、安全、成本和发行约束

- 源码、依赖、模型输入、Web 内容和导出产物分别建立边界。读取代码不等于执行代码；不能自动运行被分析仓库的未知安装脚本或 shell 命令。
- 不把秘密写入 Git、VSIX、日志、截图、checkpoint、Webview、遥测或诊断包。环境变量和工作区配置按来源审计，不跨项目混用。
- 任何新增分析/追踪服务必须透明且可关闭；不得因使用 LangChain/LangGraph 自动开启云端追踪或上传原始代码。
- 预算展示区分估计和实际。搜索次数、模型调用、失败尝试、缓存、重试和实际模型均可追踪；价格需有来源与日期，无法精算时明确说明。
- 保留经济/平衡/深度模式，但不能让经济模式关闭基本事实验证、安全检查和失败标记。
- 检查包体、激活耗时、运行时版本、native 依赖和跨平台打包。不要为了加入工具把插件变成必须搭配外部基础设施才能启动的产品。

## 十一、1.0.0 发布流程

1. 从当前版本有序升级至候选版并完成全部门槛，再统一根 package、扩展 package、lockfile、CLI、manifest、README、CHANGELOG、版本历史和验收脚本中的版本。
2. 提供首次配置、DeepSeek/Tavily 凭据、网络诊断、代理行为、隐私数据流、故障恢复、费用控制、多语言支持层级及从 0.5.x 升级的指南。
3. 检查许可证和第三方声明；不得在版权归属不明确时擅自为他人代码授予开源许可证。若需要用户选择许可方案，将它列为明确发布阻塞项。
4. 使用锁定依赖的构建环境产出 VSIX，检查打包内容，不含密钥、用户输出、测试私有数据、无关文件与旧包。生成 SHA-256 和发布清单。
5. 对实际待发布的同一个 VSIX 安装验收，记录扩展内版本、bundle 哈希、启用状态和宿主加载路径，解决“目录里有新文件但窗口仍运行旧实例”的问题。
6. GitHub Release/标签和 VS Code Marketplace 发布必须以所有门槛通过、用户既有授权和有效发布身份为前提。不要仅因拿到了 token 就忽略发布门槛，也不应在已明确获准后重复索要同一权限。
7. 只有本地打包成功不能写“已发布”；只有提交成功不能写“已上架”。分别记录构建、安装、上传、平台处理、商店可见、干净环境安装的状态和证据。
8. 发布后从实际发行渠道安装验证；如缺少账户、凭据、视觉验收或质量基准等必要条件，交付完整候选包与准确阻塞清单，继续完成其余可独立工作。
9. 提供回退版本、报告格式兼容和数据恢复说明。整个过程不得删除用户历史产物来获得“干净测试”结果。

## 十二、过程与最终交付

按以下顺序执行，并在阶段结果明确后继续推进：

1. 基线与全仓审计；
2. 本地及 Extension Host 故障复现；
3. 统一传输层与 DeepSeek 修复；
4. 证据索引、题目 schema 与内容校验升级；
5. LangChain/LangGraph 渐进集成；
6. Tavily 联网增强与对照评测；
7. 独立运行、恢复及商业化 UI；
8. 安全、性能、真实端到端与发行包验收；
9. 满足门槛后发布 1.0.0，并核验发行渠道安装。

可以并行审查相互独立模块，但由主负责人统一本次 run 的日志、模型能力、网络配置、Graph state、证据 schema 和版本策略。不要让多个子任务分别造一套重试、缓存和配置体系。

最终交付至少包含：

- 可构建源码与有解释的改动清单；
- 根因报告：区分已证实问题和未证实假设；
- 网络层设计、诊断命令和脱敏真实日志；
- LangChain/LangGraph/Tavily 实际执行链路及版本兼容说明；
- 代码证据到问题、答案和裁决的可追溯样例；
- 固定 fixture、故障注入、真实端到端和质量评测数据；
- 修复前后及搜索前后的耗时、调用量、质量和费用对照；
- 独立输出、取消、重启恢复、升级迁移的验收结果；
- 质量门槛逐项通过/失败/未测试矩阵，以及 S 评级的实际依据；
- 1.0.0 VSIX、哈希、发行文档和已完成的发布步骤；
- 剩余限制、支持平台、尚缺凭据或验收项，以及明确下一步。

先给出简短执行计划与真实基线，随后直接实施。持续工作到所有可完成的授权事项完成，不能在“单测全绿”“API 返回 OK”“扩展激活正常”时就宣布整个插件已可商业发布。
