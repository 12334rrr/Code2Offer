### P0 安全(4 项)

**S-1 密钥文件进入模型输入**
- `src/core/profiler.ts:119,279,409`、`chunker.ts:33`、`stage1Read.ts:143`
- 无敏感文件拒绝清单,`.env` 被当"配置文件"加权入选精读计划,内容原样进 prompt 发往模型端点。
- 实证†:工具根 `interview-output/repo_facts.json` 中 `.env` 同时在 `files` 与 `readingPlan`(真实运行产物)。
- 修复:独立拒绝清单(`.env*`/`*.pem`/`id_rsa*`/`credentials*`,example 模板白名单)+ 密钥模式扫描(`sk-`、`BEGIN PRIVATE KEY`)+ 首次运行展示"将读取的文件清单与目的端"。

**S-2 仓库可替换请求目的端,并与环境密钥配对**
- `src/core/config.ts:55-60`、`deepseek.ts:110-119`
- 仓库 `.env` 可写 `DEEPSEEK_BASE_URL=http://任意端点`;用户只在系统环境变量放 key 时,"环境密钥 + 仓库端点"配对成功,密钥与源码发往仓库指定端点;HTTP 明文不被拒绝。README 推荐的 `setx` 全局配置正是触发前提。
- 修复:凭据与端点绑定为同一受信配置档;仓库 `.env` 不得覆盖端点(或非默认域名首次显式确认);默认仅 HTTPS。

**S-3 跨仓库凭据污染(扩展)+ .env 优先级与文档相反(CLI)**
- 扩展 `extension.ts:139-156`:实测 A→B 两仓库,B 沿用 A 的 key/模型/端点(首仓库配置写入全局 `process.env` 永不失效,核心层又把进程变量置顶)。
- CLI `config.ts:44-53`,本轮实证†:目标仓库 `.env` 写 `model-from-target`,实际生效工具根的 `deepseek-flash`——README 承诺"目标仓库根优先(找到即停)",代码是"后读覆盖先读","给不同仓库配不同 key"失效。
- 修复:配置解析返回单次运行不可变对象,经 `RunOptions` 显式传入,不写全局 `process.env`;密钥录入用 `ExtensionContext.secrets`。

**S-4 `.gitignore` 未忽略 `.env` 本体**(只列 `.env.local`;另 `vscode/*.vsix` 5 个历史包也未忽略)。一旦 git init,真实密钥直接入库。修复:补 `.env`、`*.vsix`。

### P1 正确性(8 项,破坏 README 核心承诺)

**R-1 阶段门控与缓存键哈希族失真 → "代码变化后增量更新"承诺失效**
- runner.ts:72 画像哈希 = `v2|maxFiles|路径`,不含文件清单/内容——增删文件不刷新;
- runner.ts:95 精读哈希用 `文件名+content.length`——**等长修改不触发**(`===`→`!==`);
- runner.ts:159 校验哈希只有题号列表+分块数——题号恒为 Q01–Q100,**重出题后全新题库可整体跳过校验**†(代理复核确认);
- stage1Read.ts:125,164 模块卡/知识卡缓存键缺 `overviewJson`(prompt 的组成部分)——改未精读文件使画像变化后,精读仍全命中旧缓存†;
- stage4JD.ts:29 JD 缓存键只有题库清单长度——内容变长度不变则复用旧匹配;
- 动态复现(前轮,重跑确认):改码+增文件+改答案后二跑,画像/精读/出题/校验全命中,仅总装重跑。
- 修复:每轮先算"相对路径+内容哈希"的输入清单;各阶段缓存键纳入上游产物内容哈希+模型+提示词版本。验收:等长改码、增删文件、改答案、重出题、等长题库换 JD 均使相关阶段失效。

**R-2 校验断点按题号复用,旧裁决覆盖新题**
- stage3Verify.ts:170-185,214-256:`.verify-progress.json` 只存题号与裁决,无输入指纹,任何路径不删除它,`--force` 也不清。复现:同 ID 换题后二轮模型调用 0 次,新答案被覆盖为旧"修正答案"。LLM 幻觉 ID 也永久残留†。
- 修复:checkpoint 纳入每题输入哈希;题库重生成时删 checkpoint;返回 ID 必须属当前批次。

**R-3 校验失败/漏验/非法裁决被标为 pass**
- stage3Verify.ts:217-222,224,251-255:模型 503/空 results/漏题 → `verified='pass'`†;`verdict` 无白名单,`"Fix"`/`"ok"`/中文走 else 计入 pass†;模型 pass 可覆盖确定性错误;`q.verified` 可落盘非法字符串污染下游 `verified==='flag'` 过滤†。
- 修复:增加 `unverified/error` 状态;verdict 枚举校验;确定性错误不可被模型覆盖;未全覆盖记 partial 不标完成。

**R-4 标红题重写无事实闭环**
- stage2Questions.ts:465-495:flag 题只要回 3–6 条要点、避开元话语正则就改判 fix 并删原始警告,不复核引用(复现:0 引用+三条虚构主张 → repaired=1);校验报告不重建,题库/报告/HTML 三处状态不一致。
- 修复:改写后 `pending-recheck`,过 schema+引用+事实重验才升级;原裁决不可变留历史;报告按最终题库重算。

**R-5 "恰好 100 题"不严格,100 ≠ 满足覆盖矩阵**
- stage2Questions.ts:121-128,209:补题窗口 `slots.slice(all.length,…)` 假设"已产出数=已消耗 slot 数",任何一批坍塌后窗口漂移,丢失类别可能永远不补†;对位盲信模型返回顺序,`coerceQuestion` 用 slot 强制覆盖类别/难度——"基础"slot 可装进"刁钻"题干†;schemas.ts:106,173 `category` 只查非空字符串、不校验 ∈ CATEGORIES,且 coerce 优先采信 LLM 自报值——幻觉类别名可穿透对比块硬约束与配额统计†;`topUpToQuota` 无上限检查可补超 100,自身不经 `trimToQuota`†;不足 100 仅 warn 不阻断。
- 修复:统一"按类别×难度×目标扣除现有占用"回补;slotId 稳定,类别/难度由代码强制赋值不信模型回显;category 枚举校验。

**R-6 stage4 坏形状输出先进缓存再消费 → "重跑必崩"死锁**†
- stage4JD.ts:40-46(本轮亲自核实):`parseJsonLoose` 只保证合法 JSON 不保证形状;`关键词`/`必考ID`/`复述侧重.多讲` 被输出成字符串(jsonMode 下常见漂移)时 `.map` 抛 TypeError——**且崩溃发生在 `cache.set` 之后**,坏对象已持久化,`--force` 不清 DiskCache,此后每次重跑同 key 命中毒缓存同一行崩溃,必须手删 `outDir/.cache`。stage4 是全管线唯一缺"命中缓存也复验形状"防御的消费方(stage2Questions.ts:308-323 有,作者明知该模式)。
- 修复:照 stage2 修复环模式补形状校验 + 2 次重生成;或缓存前校验、坏形状不落盘。

**R-7 扩展:用户取消后仍启动生成;2–6 分钟长任务不可取消**
- extension.ts:34-54:QuickPick/文件选择器返回 `undefined`(取消)仍调用管线;`cancellable:false`;无 AbortSignal 贯穿(单请求 300s×3 次重试)。用户以为取消,实际继续计费。
- 修复:任何 `undefined` 立即返回;`cancellable:true` + CancellationToken→AbortSignal 贯穿全管线。

**R-8 扩展:同一目录可并发运行两条管线**
- extension.ts:16,49,54:无运行锁/按钮禁用;两管线写同一 state.json/题库/缓存互相覆盖。CLI 跨进程同样无锁†。
- 修复:目标目录运行锁(`finally` 释放),重复命令提示"运行中"。
