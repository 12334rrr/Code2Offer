## 3. 当前版本高优先级问题

### H-01 新增文件不会使画像缓存失效

**位置**：`src/core/runner.ts:193-217`。

门控检查用上次 `repo_facts.json` 的 `files` 和 `readingPlan` 重建哈希。新文件不在旧清单里，因此不会进入哈希；只要旧精读文件没变，画像直接命中缓存。新文件不会进入画像、精读、题库或校验。

**动态证据**：合成仓库首次只有 `a.ts`，写入与当前实现一致的画像状态后新增 `new-critical.ts`。再次运行日志明确显示“门控命中”，保存的 `repo_facts.json` 仍只有 1 个文件。

**影响**：新增核心模块、安全修复、路由或依赖文件后，插件可能继续输出旧项目认知。该行为直接破坏“代码变化后增量更新”和“读取完整代码仓库”的承诺。

**修复建议**：在决定是否复用画像前，执行一次低成本文件枚举，哈希“当前相对路径 + size + mtimeNs”；路径集合变化立即重做画像。高可信模式使用全文件内容哈希。不要从旧画像推导当前文件清单。

**验收**：新增、删除、重命名任意非忽略文件都必须使 profile 失效；新增文件若进入前 40 精读候选，后续 read/questions/verify 也必须失效。

### H-02 大于 100KB 的源码绕过内容密钥扫描

**位置**：`src/core/profiler.ts:85-89`、`:287-295`。

文件上限是 300KB，但内容密钥扫描只在 `content.length <= 100000` 时执行。100KB～300KB 的文件完全不做内容扫描，随后仍可被加入 `readingPlan` 并由 chunker 发送给模型。

**动态证据**：构造约 120KB 的 `large.ts`，开头放入虚构 `sk-` token。画像没有将其加入 `skippedSensitive`，并且第一个模型输入 chunk 含该 token。

**影响**：真实项目常有较大的生成源码、配置聚合文件或 bundle；一旦其中包含 token、私钥片段或测试凭据，现有“内容级密钥特征扫描兜底”失效。

**修复建议**：扫描全文件流而非只扫描小文件；至少扫描首尾和滑动窗口，且扫描必须发生在选读/切块之前。更稳妥的做法是在每个即将发送的 chunk 上再次执行 secrets 检测与脱敏。加入通用高熵和常见赋值名检测，但要将误报作为“需确认”，不要静默删除普通源码。

**验收**：101KB、299KB、token 位于开头/中间/末尾的文件均不得把命中内容放入 prompt；报告需记录跳过原因。

### H-03 仓库自带完整凭据时可控制源码发送目的端

**位置**：`src/core/config.ts:68-73`、`:94-97`、`:122-133`。

当前“端点与密钥同源”防止了环境密钥被仓库端点盗用，这是正确改进。但当被分析仓库同时提供 `DEEPSEEK_API_KEY` 和 `DEEPSEEK_BASE_URL` 时，仓库端点会被接受。对不受信任仓库而言，攻击者不需要偷用户密钥；只需提供自己的假 key 和收集端点，就能让用户把私有工作区源码发送过去。

**动态证据**：只有仓库 `.env` 的情况下，`loadConfig` 选择了虚构 `https://collector.invalid`，来源标记为“被分析仓库”。未发出网络请求。

**影响条件**：用户下载或打开第三方仓库并执行生成；仓库包含完整 DeepSeek 配置。此时数据目的端由仓库作者控制。

**修复建议**：仓库目录永远不应成为可信网络目的端来源。只从系统环境、VS Code SecretStorage、用户级配置或明确受信目录读取 key/base URL。若为了多项目配置必须允许仓库配置，首次使用非官方域名时显示目标域名、待发送文件范围并要求用户明确确认；确认记录应绑定仓库 URI 和端点证书域名。

**验收**：未确认的仓库级非官方端点不得发送任何请求；工作区信任变化或端点变化后必须重新确认。

### H-04 非空的 `finish_reason=length` 被当作完整结果

**位置**：`src/core/deepseek.ts:198-223`。

客户端只在 `content` 为空且 `finish_reason=length` 时扩大 token 预算。如果响应已有一部分文本但因长度截断，会直接返回。调用方可能将残缺 Markdown 或被宽松修复的 JSON 写入缓存，并把阶段记为完成。

**动态证据**：mock 返回非空 `## incomplete but nonempty` 且 `finish_reason=length`，客户端仅调用 1 次并原样返回。

**影响**：项目讲解、亮点、缺点、设计决策可能突然中断；JSON 修复可能把部分对象伪装成成功结构。缓存会使后续重跑继续复用残缺结果。

**修复建议**：任何 `finish_reason=length` 都必须标为 incomplete。结构化输出优先扩大预算重试；长 Markdown 可做带重叠上下文的续写并校验结尾。缓存键对应的值必须携带 `complete=true` 才能复用。

**验收**：空/非空截断、JSON 截断、Markdown 截断均不得进入成功缓存；达到预算上限后应产生明确 partial/error 状态。

## 4. 中优先级问题

### M-01 401/403/400/404 并未立即失败

**位置**：`src/core/deepseek.ts:170-195` 与 `chat()` 的统一重试逻辑。

`once()` 对永久错误抛出普通 `Error`，丢失 status；`chat()` 不识别该错误，仍按默认策略总共请求 4 次。代码注释和发布说明声称“立即失败”，实现与承诺不符。

**动态证据**：mock 401 时实际请求 4 次，警告显示 1s/2s/4s 退避。

**修复**：保留类型化 `HttpError.status/retryable`；`chat()` 对 `retryable=false` 立即抛出。为 400、401、403、404、408、429、5xx 分别加测试。

### M-02 跨进程运行锁存在检查与创建竞态

**位置**：`src/core/runner.ts:76-102`。

两个进程可以同时执行 `existsSync=false`，随后都用普通 `writeFileSync` 覆盖 `.run-lock` 并进入管线。进程内 Map 有效，但 CLI/两个 VS Code 窗口之间并非原子互斥。

**修复**：用 `openSync(lockPath, 'wx')` 原子创建；锁中加入随机 owner token，释放时只删除自己的锁。陈旧锁处理应验证 PID 是否仍存活，而非固定 45 分钟后直接抢占仍在运行的长任务。

### M-03 “完整仓库”属于过度承诺

**位置**：README 开头、`profileRepo(maxFiles=40)`、每文件最多 3 块、模块最多 12 个、单文件超过 300KB跳过。

当前实现会扫描多数文本文件建立画像，但模型默认只精读 40 个文件；每文件有块上限，超过 12 个顶层模块会被明确丢弃。这比旧版“静默丢弃”好，但仍不等于完整阅读。

**建议**：文案改为“全仓扫描画像 + 预算内重点精读”；报告展示文件覆盖率、行/字符覆盖率、被截断文件和被丢弃模块。提供高可信模式，允许用户设置 token/费用预算并做分层归约。

### M-04 正式测试没有覆盖关键编排和扩展路径

现有 46 项测试集中在 utilities/schema。缺少或不足：runner 增量门控、跨进程锁、DeepSeek HTTP 状态/截断/取消、stage1/2/4 失败恢复、evaluate、rehearse、任务时间轴、VS Code 命令及 Webview 真正运行。

版本历史声称 `runner.test.ts`、`cli-args.test.ts` 覆盖相关行为，但当前 `src/tests/` 没有这些文件；实际文件是 `cli.test.ts`，也没有 runner 集成测试。发布证据文档需要以仓库现状为准。

**建议**：优先把本报告 5 个探针反转成产品断言加入正式测试。再用 `@vscode/test-electron` 覆盖激活、生成取消、多根目录、任务去重和 Webview CSP。

### M-05 Webview 仍给磁盘 HTML 中的唯一脚本自动授权

**位置**：`vscode/src/extension.ts:525-557`。

扩展只检查“恰好一个 `<script>` + 有 head”，然后给该脚本加 nonce。若 `interview-output/index.html` 被仓库或其他程序替换为同形状恶意页面，该脚本仍被授权。异常结构下还允许用户选择“仍要在 VSCode 内打开”，此分支启用脚本且不设置 CSP。

Webview 隔离与默认 CSP 降低了宿主危害，本轮没有证明宿主代码执行；这是报告来源完整性和钓鱼风险。

**建议**：扩展用自身受信模板加载经过 schema 验证的 `questions.json`，不要执行工作区 HTML。最低限度为生成报告写入签名/内容哈希，打开前验证；结构异常只能以禁用脚本方式预览。

### M-06 发布与跨平台质量仍未闭环

- 扩展依赖 `esbuild 0.21.5`，`npm audit` 报 1 个 moderate 开发服务器漏洞。当前构建脚本没有调用 serve，实际可利用性较低，但应升级到 `>=0.25.0` 并复测。
- `activation-smoke.cjs` 硬依赖 Unix `unzip`，在本项目主要开发平台 Windows 无法运行；应改用 Node ZIP 库或 PowerShell `Expand-Archive`，并纳入 CI。
- 没有 LICENSE 和 package `license`；法律授权不明确。没有商店 128×128 PNG icon，品牌和可信度受影响。
- 本地目录保留多个历史 VSIX，虽然 `.gitignore` 已阻止新提交，但发布流程应从干净工作区构建并生成 SBOM/哈希清单。
- 0.4.0 文档写“Marketplace 待发”，应在发布后记录线上版本、发布时间和 Marketplace 安装冒烟结果。

## 5. 已修复且本轮确认有效的关键项
