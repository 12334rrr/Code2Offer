## P1-PL01：阶段缓存无法识别代码及答案变化

**定位**：`src/core/runner.ts:72`、`:95`、`:113`、`:159`；相关 JD 缓存 `src/stages/stage4JD.ts:29`。

画像哈希只有版本、maxFiles 和仓库路径，没有文件清单、文件内容或 Git 工作区状态；首次成功后新增文件、删除文件、依赖变更都不会刷新画像。精读哈希只记录文件名和字符数，`answer = 1` 改为 `answer = 2` 不会触发重读。出题哈希进一步依赖这个不完整哈希。校验哈希只有题号和分块数量，答案、引用和代码内容都可以变化而仍然跳过校验。JD 缓存只有 JD 原文和题库清单长度，两份等长但完全不同的题库会复用岗位匹配结果。

**动态复现**：运行管线一次；将两行代码中的 `1` 改为 `2`、新增 `new-module.js`、把已有题的答案改为明显不受支持的字符串；再次运行。两轮累计执行次数：

| 阶段 | 实际执行次数 |
|---|---:|
| 画像 | 1 |
| 精读 | 1 |
| 出题 | 1 |
| 校验 | 1 |
| 总装 | 2 |

保存的画像中没有新增文件，改动后的答案进入第二次总装但没有重验。JD 单独复现中，两份等长不同题库累计仅调用模型 1 次。

**影响**：继续拿旧代码讲解新项目；修复缺陷后仍然输出旧缺陷；修改题库后保留旧“已验证”状态。用户通常无法从完成提示发现这些问题。

**建议**：每轮先生成确定性的输入清单；以文件相对路径和内容哈希构建快照，纳入模型、提示词版本和所有生成参数。每个阶段记录完整上游产物内容哈希。校验对“当前题目内容 + 实际引用代码”计算哈希，并单独记录校验输入版本和输出版本，避免因修订产生无限重跑。JD 缓存纳入清单全文。文件缺失或缓存 JSON 损坏按未命中处理。

**验收**：新增/删除/重命名文件、等长代码修改、同 ID 修改答案/引用、更换模型与提示词、等长题库替换 JD 匹配均应使相关阶段失效；完全相同输入应命中。

## P1-PL02：校验断点按题号复用，会把上一轮答案覆盖到新题

**定位**：`src/stages/stage3Verify.ts:170`、`:176`、`:185`、`:215`、`:229`。

`.verify-progress.json` 只保存题号与裁决，没有仓库快照、题干、答案、引用、模型或提示词版本。完整成功后也保留该文件。新的生成通常仍使用 Q01…Q100；`--force` 仅绕过 runner 的 stageDone，没有给校验函数清理或失效这个独立 checkpoint。

**动态复现**：第一轮 Q01 得到 fix，修正答案为 `OLD ANSWER A/B/C`；第二轮将 Q01 改为完全不同题干与 `NEW A/B/C` 答案，复用输出目录。第二轮模型调用次数为 **0**，新题答案被覆盖为 **OLD ANSWER A/B/C**。

**影响**：即使调用方已经发现代码变化并请求重验，旧断点仍然阻止新校验，甚至主动覆盖正确答案；这是独立于 PL01 的第二层失效。

**建议**：checkpoint 加入运行版本及每题输入哈希；只复用完全匹配且契约合法的结果。原子写入，成功后归档或删除；force 明确创建新运行上下文。必须校验返回 ID 属于当前批次且不重复。

**验收**：保留旧 checkpoint，修改同 ID 题目；应实际重验且不能应用旧修正。中断后同快照续跑应仅补未完成题。

## P1-PL03：校验失败及缺少证据会被标成 pass

**定位**：`src/stages/stage3Verify.ts:40`、`:195`、`:218`、`:224`；runner 将结果标记为阶段完成：`src/core/runner.ts:164`。

模型调用失败、返回空 results 或漏掉某题时，只要行号检查未报错就设置 `verified='pass'`。而 `deterministicCheck` 仅遍历引用，空引用数组不会产生错误。若模型明确返回 pass，又会直接覆盖确定性错误的优先级：缺失文件也可 pass。外部返回的 verdict 没有运行时枚举校验，`green` 等字符串可落盘且统计按 pass 递增。

**动态复现**：

| 输入/故障 | 实际输出 |
|---|---|
| 模型抛出模拟 503 | pass=1；note 仅写“LLM 校验未覆盖” |
| 代码依据为空，模型 results 为空 | pass=1，deterministicIssues=0 |
| 引用 missing.js，模型返回 pass | pass=1，同时 deterministicIssues=1 |
| 模型返回 verdict=green | verified=green，pass 统计仍为 1 |

**影响**：报告中的“通过”不再意味着内容真实，服务故障会表现为高通过率。后续门控还会把这个不完整校验记为完成，重跑不一定补验。

**建议**：加入 `unverified/error` 状态；只有 schema 完整、每题有有效引用、确定性检查通过且模型给出有效 pass，才标通过。确定性错误具有不可被模型覆盖的优先级。缺题/重复 ID/未知 ID/非法 verdict 必须拒收；补验仍失败应展示真实覆盖率，阶段记为 partial，不能标完成。

**验收**：模拟 401、503、超时、空 results、漏 ID、重复 ID、非法 verdict、空引用、缺失文件，均不得新增 pass；重跑必须继续补验。

## P1-PL04：标红题仅凭三条字符串就去掉警告，没有完成事实闭环

**定位**：`src/stages/stage2Questions.ts:465`、`:478`、`:495`；执行顺序 `src/core/runner.ts:169`；旧校验报告生成 `src/stages/stage3Verify.ts:274`。

标红重写仅检查有 3–6 条要点、没有命中少量元话语正则；通过就把 flag 改为 fix，并覆写原始问题说明为“原标红主张已改正”。没有再次核对事实或要求有效引用。原校验报告已经在此前生成，改写后不重建，导致校验报告、题库、HTML 可能给出不同状态。

**动态复现**：构造无任何代码引用的 flag 题，模型返回三条明确虚构的分布式服务、百万吞吐和鉴权主张。函数返回 repaired=1，verified=fix，引用数量仍为 **0**，原始警告被删除。

**影响**：真正需要人工注意的题被包装成“已修订”，用户更可能把未核实内容直接用于面试。

**建议**：保留不可变的原裁决与修订历史；改写后状态为 pending-recheck，经过全部 schema、引用、事实重验才允许升级。引用无法恢复时保留 flag。最后统一依据最终题库重新计算报告与 HTML 统计。重验仍不能确认时明确保留人工核对提示。

**验收**：对引用为空、事实仍错误、只改措辞未改事实的修订响应，都应保留警告；报告和题库统计始终一致。

## P1-PL05：补題填错类别与难度，100 题不等于满足覆盖矩阵

**定位**：`src/stages/stage2Questions.ts:209`；`src/core/schemas.ts:173`；`src/core/runner.ts:124`。

普通生成的补题通过 `slots.slice(all.length, ...)` 选剩余题位，没有记住此前缺失的具体类别/难度。早期丢题而后期成功时，会重复最后的题位。模型自行返回不同 category/difficulty 也会被 coerceQuestion 保留。runner 只在总数不等于 100 时裁剪；总数恰为 100 的错误配额会直接通过。即使不足 100，阶段仍记录完成；trimToQuota 只能删除不能补题。

**动态复现**：只让第一批少返回 1 题，其余全部正确，补题后仍是 100 题，但：

| 类别×难度 | 要求 | 实际 |
|---|---:|---:|
| 工程化与测试×基础 | 3 | 2 |
| 核心模块深挖×基础 | 8 | 9 |

如果此时正确裁剪，也只剩 99 题。

**现有产物佐证**：仓库根 `interview-output/questions.json` 总数确实为 100，但有 **10 个类别×难度桶**与当前覆盖矩阵不一致，包括技术选型基础 3/4、核心模块基础 9/8、性能基础 1/2 等。示例项目产物 100 题且类别×难度配额全部符合。现有产物可能来自历史版本，这个快照用于说明真实数据现状；当前代码缺陷由 mock 独立证明。

**建议**：统一 runStage2 与 topUpToQuota 的“按类别×难度×目标扣除现有占用”算法；每题使用稳定 slotId，类别/难度/目标由代码强制赋值。每次补题后重新计算真实缺口；持续执行 schema、去重、配额检查；未达标输出 partial 状态和具体缺口，不得标完整成功。

**验收**：任意第 N 批少题、重复、类别漂移、难度漂移及修复轮失败后，最终必须恰好满足每个配额；预算耗尽时准确报告缺口且下次能继续。

## P2-PL06：运行时数据契约过于宽松，合法 JSON 并不保证可用材料

**定位**：`src/core/schemas.ts:144`、`:152`；`src/stages/stage1Read.ts:145`、`:157`、`:178`；`src/stages/evaluate.ts:218`、`:224`、`:262`。终端评分同类问题：`src/stages/stage6Rehearse.ts:82`、`:94`。

- 两个空表格行 `[[], []]` 能同时通过 validateQuestion 和 isValidComparison，纵使没有任何方案比较内容。未核对行宽、候选方案覆盖、单元格类型和非空值。
- 精读返回 `{}` 被转成空职责/空知识卡并正常缓存；同样输入重跑不会修复。注释所谓“兜底卡不缓存”只处理解析异常，不能防 `{}` 这种结构退化。
- 自评直接使用模型给出的数字，没有有限值与 0–10 范围校验；其余强制转换与 TypeScript 类型断言也不提供运行时保证。

**动态复现**：空比较表返回 `isValidComparison=true`、错误数组为空；`{}` 两轮精读累计只调用模型 2 次并保存 2 份空缓存；自评模拟各维度 100 分后最终打印 **85 / 10**，尽管还存在 18 项确定性失败。

**建议**：建立统一且严格的运行时 schema（可选 Zod/Ajv，也可纯函数实现），所有 API 返回与缓存读取走同一路径；数组元素非空、比较表严格矩形且覆盖候选方案、卡片包含最低信息量、分数为有限 0–10 数。无效结果单独重试，持续失败返回明确的 partial/error；不得把失败缓存为成功。

**验收**：空对象、空字符串数组、错误类型、空/非矩形表格、越界评分、非有限数、非法 status 不可变成合格产物或合格缓存。

## P2-PL07：引用消毒会制造倒置范围，范围检查接受文件末尾后一行

**定位**：`src/stages/stage3Verify.ts:58`、`:133`、`:134`。

消毒只截断结束行，不处理开始行已经在文件末尾之后。例如两行文件引用 `100-110` 被改成 `100-2`，生成了原本不允许的倒置范围。确定性检查允许 end=total+1，因此引用两行文件的第 3 行也能通过，给模型的是空摘录。

**动态复现**：`100-110 → 100-2`；同文件引用 `3` 得到 `lineErrors.size=0` 且摘录仅有标题、没有代码。

**建议**：严格定义 1-based 闭区间，要求 `1 ≤ start ≤ end ≤ actualLineCount`；对完全越界段删除并计入错误，不能把无效引用标成修复。所有引用为空须 flag；截断后的引用需要复核其支持的主张，不等于机械缩短后事实就成立。

**验收**：空文件、最后一行、末尾后一行、跨末尾、完全越界、多段中部分非法，都有确定的失败或修复策略，并保留警告。

## 其他静态质量观察（改进项，不重复计入上述动态缺陷）

1. **叙述稿与反幻觉环脱节**：`src/stages/stage5Assemble.ts:29`、`:130` 只把未经过事实重验的知识卡/模块卡作为四份叙述稿输入，没有整合阶段 3 已纠正的事实；`generateMarkdown` 直接缓存自由文本。题库即使更正，亮点/缺点/项目讲解仍可能沿用旧错误。建议维护共享的、带证据的事实层，并对叙述稿实施引用核对和与最终题库的一致性检查。
2. **排练退出与持久化**：`src/stages/stage6Rehearse.ts:104` 在追问中收到 `:quit` 只是不记录回答，没有跳出主循环；状态在 `:116` 才一次保存，中途终端退出丢失整轮成绩。建议统一命令解析，逐题原子保存；评分缺失/越界应明确失败而非按 0 或任意值积累。
3. **精读覆盖上限**：`src/stages/stage1Read.ts:35` 按顶层目录分组后取 12 个，13 模块样例实际只处理 12 个；无返回的遗漏清单。根审计另有此问题，合并报告应去重。
4. **自评不是完整验收门**：`src/stages/evaluate.ts:54` 只检查类别总数，没有检查各难度和目标配额；对比检查未使用共用 isValidComparison；样本只覆盖 12 题以内。建议把确定性质量门与模型抽样评分分开，先执行完整结构验收，再明确展示模型抽样覆盖率。

## 建议实施顺序

1. 先修 PL01–PL04：建立可信的快照与验证状态机，避免旧题和未验题显示为已通过。
2. 修 PL05、PL06：稳定 slotId、完整配额回补、严格运行时 schema，阻止坏产物进入缓存及发布流程。
3. 修 PL07 并补边界回归，统一所有阶段的引用处理。
4. 把复现脚本中的断言转为产品应满足的断言，纳入 CI；当前脚本断言的是缺陷仍然存在，不可原样作为发布成功条件。

**限制**：没有连接真实模型，因此不声称已量化幻觉率；没有真实 VS Code 用户操作和真实 API 计费测试。这里的结论限定为源码及本地可复现的管线行为。
