readBody 在请求体超过 1_000_000 字节时 reject 413 并 req.destroy()，JSON.parse 失败 reject 400，空体解析为 {}。请说明这套错误路径的设计意图，并指出「超限判断在累加之后」这一实现顺序可能带来的边界问题及修复方式。

考察点:考察对请求体读取、超限保护、错误码语义以及实现顺序导致边界失效的分析能力。

答案要点
  1. readBody 用 Promise 包裹 data/end/error 事件，累加字符串，空体解析为 {}，JSON.parse 失败 reject 400（server.js:51-70）。
  2. 超限时 reject 413 并 req.destroy()，主动断开连接避免继续接收大体积数据（server.js:53-58）。
  3. 风险：超限判断在字符串累加之后，单个 chunk 可能已使 data 超过阈值才被检测，峰值内存仍可能偏高。
  4. 改进：在累加前先判断 data.length + chunk.length 是否超限，超限立即 destroy 并 reject；验证方式是发送略超阈值的单块大 body，断言进程内存峰值与响应码。
  5. 用字符串拼接而非 Buffer 数组，大请求体下多次拼接有额外拷贝开销，可改为 Buffer 数组最后 concat。

追问1:为什么空请求体要解析为 {} 而不是报错？ 参考要点:让无 body 的请求（如某些客户端）走统一路径，后续校验对 {} 返回缺字段错误，语义更一致，避免 readBody 层与校验层重复判断。
追问2:req.destroy() 与直接 res.writeHead(413) 有何区别？ 参考要点:destroy 会直接断开 TCP 连接，阻止客户端继续上传；仅写 413 响应而不销毁，客户端可能仍持续发送数据，浪费带宽与内存。
追问3:JSON.parse 失败返回 400，为什么不是 422？ 参考要点:400 表示请求本身格式非法（不是合法 JSON），422 用于语义校验失败（JSON 合法但字段不满足约束），两者语义分层清晰。

加分回答:可补充：为 readBody 增加 Content-Length 预检，若头部声明长度已超阈值直接 413，无需读取 body；并设置读取超时防止慢速攻击。

常见错误回答:认为超限判断顺序无所谓；忽略了单 chunk 可能已超阈值导致峰值内存偏高，也未给出前置判断或 Content-Length 预检的改进。

cache.js 的 LRUCache 用 Map 的插入序实现 LRU 并带 TTL。请说明 get、set、invalidate 三个方法各自做了什么，以及为什么 get 命中时要先 delete 再 set。

答案要点
  1. 构造时校验 maxSize>0；用 Map 存储，插入序即最近使用序（cache.js:11-13）。
  2. get 命中后 delete+set 把条目移到最新端；过期则惰性删除并计 miss（cache.js:22-24）。
  3. set 时若已存在先删再插，超出 maxSize 时循环删除 Map 首元素（最久未用）（cache.js:36-39）。
  4. invalidate 直接 delete 指定 key；stats 返回 size 与 hitRate（cache.js:47-53）。
  5. get 命中 delete+set 是为了把该 key 移到 Map 末尾（最新端），保证淘汰时删的是最久未访问的条目。

追问1:为什么用 Map 而不是普通对象实现 LRU？ 参考要点:Map 保证插入顺序可预测，keys().next().value 即最久未用项；普通对象键序在整数键场景不保证插入序，无法可靠实现 LRU。
追问2:get 命中时 delete+set 的时间复杂度是多少？ 参考要点:Map 的 delete 与 set 均为 O(1)，整体 O(1)；但常数因子高于双向链表方案，因为要两次哈希操作。

常见错误回答:认为 get 只是读取不改变顺序；或以为 TTL 由后台定时器清理，实际是读取时惰性判断。

  4. 更稳的做法是 store 只暴露数据操作，由 server.js 在写成功后调用通知，保持依赖方向不变（参考 server.js 中 invalidate 调用位置）。
